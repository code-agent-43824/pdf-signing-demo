# Spike: возможности провайдеров для CAdES-BES

## Вердикт: PARTIAL

Вопрос: могут ли установленные CryptoPro Browser Plugin и Рутокен Плагин
создать канонические CMS CAdES-BES в attached и detached упаковке над одними и
теми же точными двоичными байтами?

Подготовлено:

- один двоичный fixture на 36 байт с NUL, байтами не из UTF-8 и смешанными
  CR/LF (`fixture.hex`);
- runner `public/spikes/cades-bes-runner.js` и панель
  `public/spikes/cades-bes-panel.js`. `public/app.js` подгружает их только на
  странице с `?spike=cades-bes`; обычная страница их не запрашивает. Runner
  подписывает fixture сертификатом, выбранным на странице, через реальные API
  провайдеров, на сервер ничего не отправляет и держит CMS только в памяти
  вкладки до явного сохранения файла;
- `analyze.py` принимает один или несколько файлов результата (плагины могут
  стоять в разных браузерах), требует ровно четыре результата и проверяет
  канонический DER, упаковку, побайтное совпадение вложенного содержимого,
  ровно один `signingCertificateV2`, наличие сертификата и криптографическую
  валидность через существующий верификатор RSA/ГОСТ;
- `test/cades-bes-spike.test.js` (его запускают `npm test`, CI и
  `self-test.sh`) прогоняет runner с фейковыми провайдерами, которые
  подписывают полученные байты настоящей RSA CMS на эфемерном ключе, и
  анализатор на результате; проверяет порядок вызовов провайдеров,
  fail-closed случаи, панель и то, что runner грузится только по флагу.
  Временные ключи, сертификаты и CMS удаляются после теста.

Прогон на компьютере владельца:

1. Открыть `https://mescheryakov.pro/pdf-signing/?spike=cades-bes`.
2. Выбрать плагин и сертификат, как для обычной подписи, и нажать «Подписать
   тестовые данные» в панели «Проверка CAdES-BES». Рутокен попросит PIN.
3. Переключить плагин и повторить. Если второй плагин работает в другом
   браузере — пройти там те же шаги; получится два файла.
4. Нажать «Скачать результат» и передать `cades-bes-spike.json` агенту.

Вердикт становится `VALIDATED` после анализа четырёх результатов с реальными
сертификатами: `python3 analyze.py <файл> [<файл>]`. Полученный набор
хранится только во временном локальном файле, анализируется, сводится к
безопасным полям отчёта и удаляется. Персональные CMS, имена из
сертификатов, серийные номера и отпечатки не коммитятся.

Проверяемый контракт провайдеров:

- CryptoPro: задать `ContentEncoding=CADESCOM_BASE64_TO_BINARY` до `Content`,
  затем вызвать `SignCades(signer, CADESCOM_CADES_BES, detached)`;
- Рутокен: после ввода PIN (тот же `ensureRutokenLogin`, что у подписи PDF)
  вызвать `plugin.sign(deviceId, certId, fixtureBase64, DATA_FORMAT_BASE64,
  { detached, addUserCertificate: true, addSignTime: true, addEssCert: true })`,
  для RSA-ключа, как в production-адаптере, ещё `rsaHashAlgorithm:
  HASH_TYPE_SHA256`; затем `logout`. `addEssCert` описан в публичном API
  Рутокен Плагина и по умолчанию выключен; возможность подтверждает сам
  атрибут `signingCertificateV2` в полученной CMS.

Код spike не переносится в production-адаптеры: после вердикта `VALIDATED` два
небольших метода подписи переписываются обычным образом, а панель
(`public/spikes/` и её запуск в `public/app.js`) убирается вместе со своими
тестами.
